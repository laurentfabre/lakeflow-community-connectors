01 / Understand the connector

From an Analytics dataset to governed tables

The connector reads materialized Salesforce CRM Analytics datasets through Analytics REST and SAQL. Tables are identified by dataset IDs. Salesforce sObjects such as Account and Opportunity require a different source connector.

  1. CRM AnalyticsMaterialized Default dataset + one selected version
  2. →
  3. Community readerPin schema, read all pages, validate completeness
  4. →
  5. Snapshot pipelineCompare complete snapshots by the chosen ingestion keys
  6. →
  7. Unity CatalogDelta target for current state or snapshot history

The last two stages describe the framework integration path; source-to-target behavior still needs validation on your chosen Databricks runtime.

SOURCE CONTRACT

Complete snapshots

Each capture reads every row of one version, including when that version has not changed. There is no source row-level change feed.

IDENTITY CONTRACT

Explicit keys and visibility

Use unique, non-null business keys by default, or opt into generated version/row keys for raw ingestion and later cleanup. Approve a stable integration identity with full row visibility.

PUBLICATION CONTRACT

Validate before publishing

Count, page, key, value, and metadata checks must all complete. A yielded prefix cannot be treated as a successful capture.

This community contribution has no official Databricks SLA, certification, or guaranteed compatibility. The published connector baseline is eb8a4ee on feat/connector-crm_analytics; the documented framework baseline is ddc153b. Record the exact revision you deploy.

05 / Authorize Salesforce

Configure the app and UC connection

Databricks workspace authentication and Salesforce source OAuth are separate. This connector declares shared user-to-machine authorization: one approved integration identity signs in once, and the connection layer owns token renewal and injects the current access token.

  1. Have a Salesforce administrator create an approved External Client App or use an approved existing connected app. New connected-app creation is restricted from Spring ’26; follow current Salesforce guidance.
  2. Enable authorization code OAuth with PKCE. The spec requests api and refresh_token (also described by Salesforce as offline_access). Apply your organization's app-access and refresh policies; keep the secret requirements appropriate for this confidential-client flow.
  3. Register the exact callback for the selected path. For the Databricks UI, confirm the callback shown by the workspace; the documented pattern is https://<WORKSPACE_HOST>/login/oauth/http.html. The local CLI uses http://127.0.0.1:<PORT>/callback. Scheme, host, port, and path must match; do not assume wildcard or dynamic-port acceptance.
  4. Create a COMMUNITY connection for crm_analytics through the custom connector setup. Enter the app consumer key/secret, trusted API origin, explicit REST version, and the allowlist below. Complete browser sign-in as the integration identity.
  5. Validate consent, PKCE, connection grants, refresh/rotation, runtime token injection, and the match between the authorized org and instance_url before scheduling.
SettingProduction-login default / rule
Authorization endpointhttps://login.salesforce.com/services/oauth2/authorize
Token endpointhttps://login.salesforce.com/services/oauth2/token
Sandbox / My DomainUse the approved environment's authorization_endpoint and token_endpoint overrides at connection creation. Validate them with your administrator.
Data API origininstance_url identifies the authorized org, e.g. https://example.my.salesforce.com. Do not use a generic login endpoint in place of the org API origin.

Populate CRM_CONNECTION_OPTIONS in a private shell through your approved secret tooling. Its JSON contains client_id, client_secret, instance_url, and api_version, plus endpoint overrides when needed. Keep credentials out of source files, pipeline specs, shell history, and shared logs. The CLI transports options as a command argument, which may be visible to local process inspection; use the UI or an approved private environment for secrets.

  --spec src/databricks/labs/community_connector/sources/crm_analytics/connector_spec.yaml \

The local spec selects u2m and supplies OAuth defaults. This command opens browser authorization and creates the UC connection. Do not select generic m2m or u2m_per_user modes for this connector.

Renewal is a connection responsibility. The reader itself does not refresh tokens. HTTP 401 fails immediately; renew or reauthorize the connection, then retry the complete capture. Never add an access token to the pipeline spec as a workaround.

06 / Define your capture

Configure one dataset first

Save the following as crm-analytics-pipeline.json in your checkout. Replace placeholders and example field names with values from the selected dataset's main XMD. The example assumes Account.Id and FiscalYear are string dimensions whose tuple is unique and non-null; Amount is a scalar measure.

crm-analytics-pipeline.json · bare community CLI specification
{
  "connection_name": "crm_analytics_connection",
  "objects": [
    {
      "table": {
        "source_table": "<DATASET_ID>",
        "destination_catalog": "<CATALOG>",
        "destination_schema": "<SCHEMA>",
        "destination_table": "account_analytics",
        "table_configuration": {
          "source_primary_keys": ["Account.Id", "FiscalYear"],
          "selected_columns": ["Account.Id", "FiscalYear", "Amount"],
          "supported_scope": "scalar_full_visibility",
          "scope_fingerprint": "<APPROVED_STABLE_VISIBILITY_SCOPE>",
          "version_id": "<PINNED_VERSION_ID>",
          "column_name_mode": "readable",
          "decimal_precision": "38",
          "decimal_scale": "18",
          "max_keys": "1000000",
          "max_query_requests": "2000",
          "max_read_seconds": "1800",
          "scd_type": "SCD_TYPE_1"
        }
      }
    }
  ]
}

Source keys use original physical names. Normally omit primary_keys: the connector supplies the destination names, e.g. Account__Id. A dataset ID identifies a table, not an individual row. The scope fingerprint should be a stable operator-managed label for the approved identity/visibility contract, never a token, run ID, or timestamp.

Land duplicate business keys for downstream cleaning

Set auto_increment_column to an output name to preserve raw rows, including identical duplicates and null business keys. For example, use this table_configuration with a new raw destination:

Raw snapshot · table_configuration
{
  "scd_type": "SCD_TYPE_1",
  "auto_increment_column": "_ingestion_row_id",
  "selected_columns": ["Account.Id", "Region", "Amount"],
  "supported_scope": "scalar_full_visibility",
  "scope_fingerprint": "<APPROVED_STABLE_VISIBILITY_SCOPE>"
}

The connector adds _ingestion_row_id (BIGINT, 1 through N per pinned version) and _crm_analytics_version_id (STRING). Their pair becomes the destination primary key. source_primary_keys is optional in this mode; if retained, its names must still be physical projected fields. Omit the common primary_keys override and keep generated names out of selected_columns.

Numbers restart at 1 for each source version. The reader orders by every projected physical field before numbering and retains all occurrences of identical rows. The version component prevents number reuse from linking unrelated rows across versions. With SCD_TYPE_1, a new version replaces prior-version rows in the raw target. Clean and deduplicate by business rules in a subsequent table. This option provides neither a global counter nor a business ID stable across versions; SCD Type 2 histories describe versioned snapshot rows.

Redeploy the updated source or wheel and add auto_increment_column to an existing connection's externalOptionsAllowList. Enabling, disabling, or renaming the option changes schema and keys: use a new destination or explicitly migrate the target/checkpoint. Generated names must not collide with physical destination names. Count, page, scalar-value, metadata, visibility and budget checks remain active. Generated uniqueness cannot independently establish source uniqueness or detect every repeated/missing source row; validate full row/value multiplicities and pagination on the real source.

Create and run an evaluation pipeline

The repository CLI's default path builds and uploads both wheels to a UC Volume and creates a managed ingestion pipeline. It accepts the bare spec above. These are evaluation setup commands; the connector's managed runtime behavior remains a live-validation gate.

How this spec relates to other deployment paths

This is a community CLI input, not a direct request body for databricks pipelines create --json. A full managed API body uses ingestion_definition and an appropriate environment/dependency configuration; let the repository tooling assemble it and validate it in your workspace.

The legacy --use-workspace-pipeline path clones a repository and runs an ingest.py entrypoint; the source README shows the corresponding pipeline_spec wrapper. If you use that path, explicitly configure this fork and the CRM Analytics branch, since generic tooling defaults may point to upstream. Do not mix the three input shapes.

A fixed pin intentionally reads a fixed version. Before each new capture, orchestration must resolve the intended new version and pass that same version_id through schema discovery and extraction. The stock reader does not supply a version-advancement scheduler. Omitting the pin across independent Spark contexts can resolve different versions and is unsafe.

Schedule after acceptance

Use triggered runs, scheduled through a Lakeflow Job after the dataset refresh and version-resolution step. Set the cadence from measured refresh timing, extraction duration, and source quotas. Test unchanged versions, overlapping triggers, refresh races, restarts, and expired versions before enabling a recurring schedule.

08 / Preserve meaning

Data, names, and deletion behavior

Data type mapping

Physical source fieldDestination typeBehavior

Column naming and upgrades

Readable mode preserves ASCII letters/digits/underscores, changes dots to double underscores (Account.Id → Account__Id), and escapes other code points as _uXXXX_ with lowercase hexadecimal. Digit-leading names and the reserved name none receive c_. Original names remain in Spark field source_name metadata and descriptor column_mapping.

Case-insensitive collisions fail: Account.Id with Account__Id, or Id with id. Resolve the source schema, explicitly exclude a non-key collision, or deliberately use legacy_hex, where Account.Id → c_4163636f756e742e4964. Escaping can expand long names; the implementation has no destination-name-length guard, so validate names against the target runtime's limits.

Existing hex-named targets must retain legacy_hex until an approved migration. Naming mode, source keys, projection, visibility, and schema define the data contract. All-column mode and explicit selection have different configuration identities even if they currently select the same fields. Review externally keyed state after upgrading to the projection-aware fingerprint. Budget-only tuning does not change the data fingerprint.

Empty snapshots, updates, and deletes

A successful snapshot is the complete current row population of the pinned version under the approved scope. The framework can compare it with the prior accepted snapshot to infer inserts, updates, and removals. A positively validated empty snapshot can remove all prior rows. An unchanged version still returns the full row set.

Never substitute empty data for an error. A 403, missing version, shortened page, invalid ingestion key, count mismatch, warning, or failed validation is a failed capture. Strict mode also rejects duplicate/null business keys; generated mode preserves them explicitly. Discard rows from a failed attempt. Permission loss and visibility changes must not be interpreted as business deletions.

Count and metadata checks cannot detect every equal-count permission or value change. Full visibility is an operator contract that needs independent source-to-target validation. Salesforce does not guarantee unlimited historical version retention or immutable XMD/security properties. Snapshot history also cannot recover updates that occur between captures.

09 / Run with evidence

Sizing, monitoring, and recovery

Estimate the minimum query allowance

A retry-free capture requires at least:

SAQL attempt lower bound
ceil(totalRowCount / page_size) + 3

# 407 rows at page_size 100: 5 data pages + 2 counts + 1 terminal = 8
# A positively validated empty dataset still needs 3 attempts.

Failed attempts and retries consume max_query_requests; metadata GETs do not. A budget below the minimum is rejected before SAQL extraction. The allowance is per read, not an org-wide quota. Discovery pages contain up to 200 datasets and are separate from extraction page_size.

Memory grows with the complete key-validation set. Estimate using representative key widths and available executor memory; max_keys is a guard, not a capacity recommendation. Elapsed time includes consumer delays and retries. Raising budgets does not solve offset-pagination cost or source limits; validate high offsets and representative sizes live.

Capture these operational signals

  • Dataset/version, integration scope reference, package/framework revisions, projection/naming mode, expected/extracted/target counts, and capture start/end.
  • Pipeline/update IDs, final state, failures, retries, source quotas, duration, and target freshness relative to the intended dataset version.
  • Completed source read evidence: query_requests, elapsed_seconds, max_query_requests, and max_read_seconds. The reader's get_read_evidence helper only succeeds after full exhaustion; automatic dashboard publication of these values is not supplied.

Monitor final pipeline state and retained target state as well as reader evidence. Reader completion alone does not prove atomic downstream Delta application. Keep secrets, OAuth grants, cookies, and business-row payloads out of support logs.

Recover a failed capture

  1. Pause recurring runs if failures involve identity/visibility, incomplete data, or repeated source pressure. Preserve the last accepted target and its evidence.
  2. Investigate the exact failed version, key contract, source response category, permissions, and budgets. Reject the partial attempt; do not mark it complete.
  3. Retry the entire same pinned snapshot if it remains available and valid. If it expired, select a new approved capture/version rather than silently substituting one into the failed attempt.
  4. Validate source-to-target equality and restart/retry behavior before resuming the schedule. Do not reset checkpoints, enable full refresh, or replace the baseline without assessing target and history impact.

For upgrades, preserve the deployed artifacts/spec and test the replacement against an isolated destination first. Rollback requires compatible package, schema, keys, scope, and checkpoint state; do not assume a package downgrade reverses a data migration.

10 / Diagnose a failed run

Troubleshooting playbook

Start with the final pipeline/update status, the failed dataset/version, and a sanitized error. Every failed extraction requires a complete retry after the cause is resolved.

Publication succeeds but the named tile is missing, or opening the asset fails

Use the Setup URL printed by community-connector publish. Named tiles require workspace support for saved-connector discovery; saving an asset alone does not establish that support. Opening the asset through the workspace file editor can return Unexpected NodeType: type=communityConnector. A setup request can also fail with No access to read file when the workspace cannot export that special asset type. The updated CLI detects this specific export failure, saves an ordinary .setup.json manifest, and checks its complete readback before reporting success. Update your checkout and installed CLI, then republish with --overwrite. Other permission, network, or content-validation errors still need to be resolved. See workspace publication.

“Create connection” is disabled or requires CREATE_CONNECTION

Hover the action to check its required grant. Have the metastore administrator grant CREATE CONNECTION to the intended creator, or provide an approved existing connection with the required usage rights. This grant is independent of publishing the connector and staging wheels. Salesforce app credentials and consent are still required once connection creation is available.

Publication fails because the schema or wheel Volume is unavailable

Confirm the selected profile and use an existing schema in a writable Unity Catalog catalog. A read-only Delta Sharing catalog cannot host the new staging schema or Volume. If the tool needs to create the managed Volume, the publishing identity needs the relevant schema creation rights; upload and runtime installation also need the appropriate Volume write and read grants. Resolve the reported catalog/schema/Volume error before republishing.

OAuth callback rejected, browser error, or consent fails

Compare the complete requested URI with the app registration. Check the UI host or exact http://127.0.0.1:<PORT>/callback used by the selected local CLI. Use --redirect-port for a deliberate fixed local port. Confirm production/sandbox/My Domain endpoints, app access, PKCE, and requested scopes. Validate UI and local CLI paths separately; do not relax app policies or assume wildcard acceptance.

HTTP 401 / “authentication expired or invalid”

Renew or reauthorize through the UC connection, then retry the full snapshot. Check refresh-token policy and current-token injection into runtime requests. The reader does not renew tokens, and a Databricks workspace token is not a Salesforce access token.

HTTP 403, missing dataset, or missing / expired version

Verify the integration identity, API entitlement, sharing/security predicates, dataset type, API version, and exact dataset/version IDs. Discovery includes only materialized Default datasets. Do not substitute a different dataset or a new current version into an existing attempt. Investigate permission changes before allowing snapshot-inferred deletes.

“Unexpected dataset type” for a materialized default dataset

Update the connector and regenerate/redeploy the merged source or rebuild the source wheel. Earlier revisions compared response datasetType only with "Default", incorrectly rejecting lowercase "default". The corrected response check accepts either casing; the discovery request remains datasetTypes=Default. Other dataset types remain unsupported.

Count mismatch, short page, warnings, or metadata drift

Abort publication. Recheck the pinned version, source refresh/retention, full visibility, stable ordering, and selected field metadata. Validate all pages and the terminal empty page. A count match alone does not prove value fidelity or constant permissions. Empty aggregate results are not accepted as affirmative proof of zero rows.

“Null or duplicate primary key in snapshot”

For strict business-key ingestion, confirm the dataset grain and use the required physical string dimensions/date-string fields in source_primary_keys. If the intent is to land raw duplicates and clean them downstream, enable auto_increment_column with a new raw target or an explicit migration. The version/row pair then identifies each raw row; business-key duplicates and nulls remain available for later cleanup. Avoid a business-key primary_keys override.

Unsupported XMD, date roles, multivalue fields, or decimal overflow

Compare main XMD with real values. Explicitly select supported scalar physical fields and every key; malformed metadata still fails even for unselected fields. Date role overlaps are conservatively rejected. Configure sufficient decimal precision/scale without rounding. Treat selected schema changes as a migration decision.

Invalid selected_columns, destination keys, or unknown table options

Use a nonempty JSON array of distinct physical source names, including all source keys. Put source options in table_configuration and credentials in the connection. Verify externalOptionsAllowList against the local spec. Normally omit primary_keys; if used, it must contain mapped destination names in source-key order. Remove filters, sample caps, and unsupported options.

“Unknown table option” names token-expiry or UC connection metadata

access_token_expiration, refresh_token_expiration, externalOptionsAllowList, and sourceName are connection metadata supplied alongside the OAuth token. Update and redeploy the connector: the corrected _table_options() transport allowlist excludes these keys, case-insensitively, from table validation and snapshot fingerprints. Metadata changes do not change the source data contract. Keep these fields in the connection; they do not belong in selected_columns or as table options. Token renewal remains the connection layer's responsibility.

“selected_columns contains an unknown physical field”

At least one requested name is absent from the pinned dataset version's main XMD physical inventory. The check prevents a requested column from silently disappearing. Read the exact, case-sensitive names from xmdMain.dimensions[].field, xmdMain.measures[].field, and the values of xmdMain.dates[].fields in the version response obtained with filterGroup=Medium. Use Account.Id, not its destination name Account__Id; use Amount, not amount. Explorer labels and logical date names may differ from physical names. Check that the metadata belongs to the dataset and version being read.

The updated error lists unmatched fields and case or destination-name hints, or a short sample of available physical fields. Correct selected_columns using those source names and keep every source key. Hints do not automatically rename fields or weaken validation. Replace the deployed generated source or wheel to receive the new diagnostic.

Destination column collision or target name-length failure

Inspect case-only, dot/underscore, and escaped-name collisions in the projection. Rename the source field, exclude a non-key conflicting field, or deliberately choose legacy_hex with a new baseline/migration. Check expanded mapped-name lengths against runtime limits; there is no connector length guard. Never silently rename existing keys.

max_keys, query budget, or elapsed budget exceeded

Discard the incomplete read. Assess full-snapshot key memory, the query lower bound, retries, offset cost, network duration, and downstream pauses. Increase limits only within an approved measured resource envelope, then retry the full read. No budget setting is a supported row-sampling mechanism.

HTTP 429 / 5xx, repeated timeouts, or Retry-After beyond policy

Check Salesforce quotas and observed request duration. Reduce concurrent captures or retry later. Tune transport limits and scheduling using measured cost. The reader retries only the configured transient categories and honors its delay cap by aborting when necessary. Do not shorten a server-supplied delay to force an earlier retry.

Pipeline succeeds but data stays on an old dataset version

Inspect version_id and the orchestration step that resolves pins. A fixed version intentionally rereads the same data. Publish a new consistent pin for the next capture and compare the intended source refresh with target freshness. Verify the integration identity still sees that version.

Wrong workspace, missing connector, wheel, or UC permission error

Verify DATABRICKS_CONFIG_PROFILE, conflicting host/token environment variables, and the Databricks CLI --profile. Run setup from this fork's checkout. Confirm community capability, matching framework/source wheels, source name crm_analytics, Volume access by the execution identity, and destination grants. Use the CLI's actual --help if a flag differs from this guide.

Unexpected target removals or identity / sharing change

Pause the schedule and preserve the last accepted target/evidence. Compare identity, sharing rules, security predicates, scope fingerprint, keys, projection, and schema with the approved baseline. A permission change can have the same row count and escape count checks. Approve an explicit baseline/migration and recovery plan before continuing; do not merely change the fingerprint and reuse deletion history.

11 / Make the handoff repeatable

Customer and partner rollout

Start with a small representative dataset, then expand only after the source contract and runtime behavior are established. The 30 October 2026 offline source suite records 389 passing tests and 2 expected skips, including 48 metadata/projection and 52 generated-row identity regressions across the package and generated deployment source. The registry suite adds 9 passing tests. These are synthetic results, not customer certification.

Evaluation acceptance checklist

  • Confirm OAuth callback, PKCE consent, refresh/rotation, runtime token injection, and the authorized org/identity.
  • Read a multi-page dataset and compare every key and value with the pinned source, including decimals, dates, Unicode, leading zeros, and nulls.
  • Test source refreshes, unchanged versions, expired pins, version-resolution races, and actual XMD/date/empty-count shapes.
  • Exercise inserts, updates, transitions to null, removals, and a positively empty dataset in an isolated deletion-sensitive target.
  • Prove partial reads, source failures, permission loss, and failed final validation do not publish partial or empty results.
  • Verify actual Spark/Delta behavior, full retries, checkpoint restarts, and idempotent recovery across interrupted runs.
  • Agree on additive schema evolution, incompatible-change policy, projection/naming migrations, and baseline approval.
  • Measure representative volume/high offsets, total API use including retries/metadata, memory, runtime, compute cost, and two refresh cycles against the agreed freshness objective.
  • Confirm target governance, credential owner, incident response, schedule ownership, and a tested rollback/recovery plan.

Partner handover package

Provide a sanitized spec; exact repo commit and wheel versions/checksums; workspace/runtime and pipeline/update IDs; dataset/version and approved scope references; source-key and naming mappings; full reconciliation results; measured operating envelope; known limitations; and named source/platform/support owners. Share credentials only through the customer's approved secret channel.

Archive requirements need their own scope. If a customer needs immutable snapshot storage or ordered replay, design and validate that application separately: durable completion, writer fencing, publication order, schema evolution, idempotent recovery, and retention for pending consumers. These capabilities are not delivered by this connector package.

Cost and commercial expectations

Budget for Databricks pipeline compute, wheel/artifact and Delta storage, optional job orchestration, and Salesforce API/CRM Analytics entitlements and quotas. Each scheduled capture reads the full selected snapshot. No connector-specific benchmark, pricing guarantee, maximum safe volume, or freshness SLA has been established; measure the intended workload and confirm current vendor pricing.
